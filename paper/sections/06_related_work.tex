\section{Related Work}
\label{sec:related}

\paragraph{LLM serving engines and phase scheduling.}
Modern LLM serving systems improve execution efficiency through
iteration-level batching and KV-cache management~\cite{orca,vllm},
scalable and parallel inference~\cite{pope_scaling_inference,
deepspeed_inference,alpaserve,loongserve}, optimized attention and
speculative execution~\cite{flashattention2,specinfer}, and structured or
adapter-multiplexed serving~\cite{sglang,slora}.
A complementary line of work explicitly manages the distinct resource demands
of Prefill and Decode.
Sarathi-Serve uses Chunked Prefill to reduce Prefill--Decode interference
~\cite{sarathi}, DistServe disaggregates the two phases and provisions them
against latency objectives~\cite{distserve}, and Splitwise and ShuffleInfer
similarly separate or coordinate phase execution to reduce interference
~\cite{splitwise,shuffleinfer}.
These systems primarily improve how admitted work executes.
RAVEL operates at a different control layer: it determines geographic
placement and preserves bounded placement revisability before engine handoff,
while relying on the local serving engine to execute admitted requests.

\paragraph{Distributed and cache-aware LLM routing.}
Distributed serving systems increasingly route requests using runtime load,
reusable KV state, and adaptive scheduling signals.
Preble jointly considers reusable KV state and computation load
~\cite{preble}, while DualMap balances cache affinity against load and performs
hotspot-aware rebalancing~\cite{dualmap}.
Other work explores learned or adaptive request scheduling
~\cite{llm_learning_to_rank,simple_is_better,lodestar}.
A related body of work improves KV-cache reuse, storage, and transfer through
cache-centric serving and prefix-aware execution
~\cite{mooncake,cachedattention,infinigen,cachecraft,chunkattention,
cacheblend,kvlink}.
These techniques improve destination selection or reduce the cost of executing
a request at a selected destination.
RAVEL does not introduce a new cache primitive or routing score.
Instead, it separates destination selection from commitment:
an arrived request contributes prospective demand to its tentative replica
immediately, while that replica may still change before successful engine
handoff.

\paragraph{Geo-distributed and network-aware placement.}
Recent systems explicitly incorporate geographic and network heterogeneity
into LLM placement.
SkyWalker balances cross-region load while preserving KV-cache locality
~\cite{skylb}; GORGO incorporates WAN latency, queueing state, and
Prefill/cache cost into cross-region decisions~\cite{gorgo}; and Solyx uses
serving telemetry together with WAN measurements for per-request cross-site
placement~\cite{solyx}.
Helix further considers heterogeneous GPU and network resources in LLM serving
~\cite{helix}, while network-aware ML schedulers such as CASSINI coordinate
placement with communication conditions~\cite{cassini}.
More broadly, private-WAN systems such as SWAN and B4 demonstrate the
importance of heterogeneous inter-datacenter paths and traffic constraints
~\cite{swan,b4}.
These systems sharpen the decision of \emph{where} work should execute.
RAVEL makes an additional control decision first-class:
\emph{when should that placement become irreversible?}
It answers this question by retaining Router-owned tentative placement and
prospective accounting until the engine-handoff boundary.

\paragraph{SLO- and application-aware LLM scheduling.}
Prior systems adapt LLM execution and routing to request-specific latency,
deadline, or quality objectives.
JITServe schedules heterogeneous request classes from imprecise request
information~\cite{jitserve}, QUARTZ targets TTFT SLOs through
quantile-aware routing and queueing~\cite{quartz}, Andes considers
quality-of-experience for streamed generation~\cite{andes}, and AdaServe
customizes speculative decoding to per-request SLO requirements
~\cite{adaserve}.
Libra combines request partitioning with SLO-aware scheduling under dynamic
load~\cite{libra}, while complementary work studies serving fairness, SLO
metrics, and serving-performance characterization
~\cite{fairness_llm,revisit_slo_goodput,vidur}.
Application-aware systems exploit structure across related LLM calls:
Parrot coordinates semantic dependencies across requests~\cite{parrot},
Agentix schedules agent programs as first-class execution entities
~\cite{agentix}, and Ayo optimizes end-to-end LLM applications
~\cite{ayo}.
Agent frameworks and benchmarks further expose increasingly multi-stage and
dependency-rich workloads~\cite{autogen,gaia,agentbench,webarena}.
RAVEL applies request-specific SLO semantics at a different control point:
it uses WAN delay and replica serving state to determine which geographic
capacity remains feasible before handoff, while its engine-local controls
preserve the execution assumptions used by those placement decisions.

\paragraph{Reassignment, migration, and online commitment.}
Serving systems can preserve flexibility after an initial assignment through
runtime migration, state movement, preemption, or dynamic orchestration
~\cite{llumnix,spotserve,serverlessllm,dejavu,dlora}.
Llumnix, for example, dynamically reschedules requests across model instances
and uses live migration to improve load balancing and isolation
~\cite{llumnix}.
These mechanisms retain placement flexibility after engine-managed execution
state has materialized.
More broadly, delay scheduling shows that waiting can expose better placement
opportunities~\cite{delayscheduling}, while deadline-aware and online
scheduling systems study finite slack, incomplete information, and scalable
decision making
~\cite{liu_layland_edf,sparrow,flow_imprecise,omega,firmament}.
RAVEL chooses an earlier commitment boundary.
A request may be reassigned while it remains Router-owned, but its placement
becomes final after successful engine handoff, before changing placement would
require moving engine-managed request state.
Pre-handoff replanning and runtime migration are therefore complementary:
the former can avoid some state movement, while the latter can correct
imbalance that emerges after execution begins.
